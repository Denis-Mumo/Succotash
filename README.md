# QR Security Assessment Platform

A local-first, privacy-conscious assessment tool for authorized security-awareness campaigns. It records requests against active QR codes and supports aggregate analysis by campaign and approved office location. A request is an observation; it is not proof that a person scanned a code.

## Requirements

- Node.js 20 or later and npm
- Windows, macOS, or Linux
- HTTPS in production

## Local setup

```sh
npm install
cp .env.example .env
npm run migrate
npm run create-admin
npm run dev
```

On Windows PowerShell, copy the example file with `Copy-Item .env.example .env`. Set `SESSION_SECRET` in `.env` to a randomly generated value of at least 32 characters before starting. The administrator creation command prompts for an email and password; passwords must be at least 12 characters and are stored as bcrypt hashes. There is no public sign-up or default administrator.

Open <http://localhost:3000/login>. Create a campaign and approved locations, activate the campaign, then open **QR Codes → Generate codes**. After generation, use **Download PNG** on each code or **Print sheet**. The sheet remains available after the inventory refresh and while the dashboard tab stays open. QR tokens are stored as SHA-256 hashes, so after a full page reload the raw token/image cannot be recovered from inventory; save the PNGs or generate replacements before closing the page.

## Demo data

Demo data is fictional and opt-in. In a development environment, run `SEED_DEMO=true npm run seed` (PowerShell: `$env:SEED_DEMO='true'; npm run seed`). The seed creates a draft campaign and inactive QR inventory. Seeded locations are marked as fictional; do not use sample activity as real campaign results.

## Useful commands

| Command | Purpose |
| --- | --- |
| `npm run migrate` | Apply schema migrations |
| `npm run create-admin` | Create an administrator interactively |
| `npm run set-admin-role` | Grant or remove the privacy administrator role from an existing administrator, interactively |
| `npm run dev` | Start with Node watch mode |
| `npm start` | Start the production server |
| `npm test` | Run the automated test suite |
| `npm run retention` | Remove expired unattributed scan events using campaign retention settings |

Run the retention command from a scheduled job appropriate to your deployment. Attributed records are retained by this basic utility and require a separate approved review before deletion. Reports, audit records, and campaign records are preserved; review and apply organization policy to these records.

## Configuration

Copy `.env.example` to `.env` and set:

- `NODE_ENV=production` for production. A session secret of at least 32 characters is mandatory.
- `SESSION_SECRET` to a secret generated outside source control. Rotate it as an incident response action (existing sessions will expire).
- `DATABASE_PATH` to a persistent, access-controlled path outside the public web root.
- `PORT` to the listen port.
- `TRUST_PROXY_CIDRS` to a comma-separated list of exact trusted reverse-proxy IPs/CIDRs only when behind those proxies. Leave it blank for direct access; Express then ignores `X-Forwarded-For`.
- `DISPLAY_TIMEZONE` to an IANA timezone such as `UTC` or `Africa/Nairobi` for dashboard display. Stored timestamps remain UTC.
- `LANDING_MESSAGE` to an approved, non-sensitive organization message. The rendered value is HTML-escaped.
- `RETENTION_DAYS` as the default retention period for new campaigns. Campaign-specific retention is stored on each campaign.

The existing `scan_events` table already held QR, campaign, placement/location, and `occurred_at`; that timestamp remains the canonical `scanned_at_utc` value and is generated by the server as ISO 8601 UTC with millisecond precision. Migration `004-scan-source-ip.sql` adds `source_ip` (existing events receive `unknown`) and indexes source IP and QR-code ID; the existing timestamp index remains. The public scan endpoint stores the IP resolved by Express with each event. IPs are personal/network metadata: restrict scan-log access to authenticated administrators, document the purpose and retention period, protect database files and backups, and delete records under the campaign's configured retention policy. The app does not persist cookies, authorization headers, or full user-agent strings; it stores only a coarse user-agent category and request method. It does not collect MAC addresses or fingerprint devices. A unique source IP is not a unique person or device.

## HTTPS deployment

Terminate TLS at a maintained reverse proxy or managed load balancer. Set `TRUST_PROXY_CIDRS` to the proxy's exact source IP or narrowly scoped subnet, and firewall the Node port so only that proxy can reach it. Do not trust all proxies or use a broad untrusted network. Leave the setting blank when Node receives direct client connections; in that mode Express ignores forwarded-for headers and uses the socket peer address. Configure the proxy to overwrite incoming forwarded-for headers with the actual peer address (or append them only under a reviewed chain), set `X-Forwarded-Proto: https`, redirect HTTP to HTTPS, set request-size and connection limits, and use a valid certificate. Under `NODE_ENV=production`, the session cookie is `Secure`, `HttpOnly`, and `SameSite=Strict`. The app uses Helmet security headers and a same-origin check on administrative requests. Restrict CORS at the infrastructure layer; this app does not enable cross-origin API access.

Place the SQLite file and backups on encrypted, access-controlled storage. Use a single application host for SQLite session and app storage unless the database/session layer is replaced with a supported shared service. Back up the database using SQLite's online backup mechanism or a coordinated stopped-service backup; test restoration.

## Event classification and limits

- A valid GET records an **unclassified request**, except request user-agent strings matching common bot, crawler, preview, or CLI patterns are labeled **likely automated**. This is a heuristic and can be wrong in either direction.
- A deliberate POST on the landing page changes the matching unclassified event to **possible human**. Automated clients can submit forms too, so this is not confirmation of a person.
- The system does not set **confirmed human** automatically. An administrator may review a classification only with a documented evidence basis; IP address or user-agent alone is insufficient.
- A unique possible-interaction code count is the count of distinct QR codes with a follow-up action. It is not a count of people. Repeat requests remain available as events and are counted separately from unique code estimates.
- Link scanners, previews, and security crawlers may fetch a URL. Exposure, endpoint requests, follow-up actions, and person-level behavior are separate concepts.
- Shared-location events are not attributed to an employee. Individual mapping/import and access are available only to the `privacy_admin` role. The administrator CLI creates the normal `admin` role only; use `npm run set-admin-role` from a trusted local operator account to grant the privacy role, and keep that access narrowly assigned.
- No GPS, camera, microphone, device fingerprinting, credential collection, or external redirect is implemented. No employee failure percentage is calculated without a denominator.

## Privacy and retention

Use only approved locations, campaigns, messages, and assessment methodology. Keep the application on organization-controlled infrastructure, communicate applicable notice and governance requirements, and assign a data owner before launch. The default retention task removes expired, unattributed scan events, including source IPs, using each campaign's retention period. It leaves attributed events, reports, campaign metadata, and audit logs in place. Establish and document how those remaining records are reviewed and deleted under policy. A backup and retention process must follow the same policy.

Participant imports and identity mapping require a privacy administrator and are separate from event rows. Attribution records require a participant reference, a documented basis, and a confidence level. A shared QR event must not be attributed from network information, device signals, or inferred location. Viewing participant mappings creates an audit entry.

## Troubleshooting

- **Cannot sign in:** Run `npm run create-admin`, confirm `DATABASE_PATH` points at the migrated database, and check that browser cookies are enabled.
- **Server says database is not initialized:** Run `npm run migrate` with the same environment and database path used by the server.
- **QR scan returns not found:** Confirm the campaign is active, code is not revoked, token URL is complete, and its location is active.
- **Login works but edits fail:** Refresh the page to acquire a CSRF token; ensure a proxy preserves the request host and same-origin scheme/host.
- **Client IP/rate limiting behaves unexpectedly:** Leave `TRUST_PROXY_CIDRS` blank for direct access. Behind a proxy, verify the observed peer address and configure only that proxy's address/CIDR; prevent direct access to Node.
- **SQLite busy/locked:** Avoid multiple app instances on one SQLite file, use persistent local disk, and keep concurrent writers low.

## Tests

`npm test` runs the Node built-in test runner. Tests create an isolated temporary SQLite database and exercise public/admin access boundaries, login and CSRF, campaigns, locations, QR generation, scan recording, source-IP capture with IPv4/IPv6 proxy scenarios, spoofed-header rejection when proxy trust is off, UTC timestamps, invalid/revoked tokens, event filters, unique-IP counts, retention-compatible records, and filtered CSV exports.
